# 第 09 章：std::shared_ptr：AdditionalOutputs 的共享读取与可选扩展

## 学习目标

shared_ptr 在 ASPECT 材料模型中常用于“一个输出对象被多个逻辑块观察或填充”。 读完本章，你应该能回答三个问题：这个数据结构保存什么，代码在什么时候修改它，以及为什么它比更简单的变量更合适。ASPECT 是大型并行有限元程序，很多初学者第一次读源码时会被模板、命名空间和物理术语压住；本教材把视线缩小到数据结构本身，让你先抓住 C++ 程序如何组织数据。

本章源码锚点：`source/material_model/melt_boukare.cc; cookbooks/phase_transition_kinetics/phase-transition-kinetics.cc`。

主要案例函数或逻辑块：`MaterialModelOutputs::get_additional_output_object 相关逻辑`。

## 先验 C++ 概念

你需要知道变量、类型、函数、引用、`const`、循环和条件判断。还需要知道模板写法 `T<...>` 表示“同一个容器或类可以装不同类型”。ASPECT 代码里经常出现 `template <int dim>`，它表示二维和三维共用一份源码；因此容器大小可能跟 `dim`、四边形/六面体单元、速度分量数、组分场数量或 MPI 分区有关。

初学者读 ASPECT 时不要试图一次理解所有物理。先问：数据从哪里来，暂存在哪里，什么时候被加到另一个容器里，最后交给谁。这个读法对所有章节都适用。

## 场景解释

在 ASPECT 中，容器很少是为了“演示 C++”而存在。它们通常服务于一个数值计算流程：先在单元、面、积分点或物理场上收集局部数据，再做局部计算，再把结果汇总、转换、输出或传给求解器。也就是说，容器承担的是科学程序里的记账工作。记账准确，物理公式才有落脚点；记账混乱，公式再漂亮也会写错位置。

本章案例的第一层意图是建立一组临时数据。临时数据不是坏设计，它反而是高性能有限元代码中很常见的做法。每个单元或每个积分点都会重复使用同一批缓冲区，避免在内层循环里反复申请内存。初学者常常只关注容器里“有几个数字”，但 ASPECT 更关心这些数字和网格、自由度、物理场、边界、MPI rank 的对应关系。

第二层意图是保持顺序或对应关系。很多容器本身并不携带物理名字，例如一个 `double` 数组只知道第 0、1、2 个位置，并不知道这些位置分别是哪个组分或哪个边界。ASPECT 通过 `introspection()`、boundary id、变量名映射、block index 等外部结构赋予它意义。这是读源码时最重要的技巧：容器保存值，周围的索引体系解释值。

第三层意图是把局部结果变成全局结果。ASPECT 通常运行在 MPI 并行环境里，一个 rank 只拥有部分网格单元。局部容器里的统计量不能直接代表整场模型；它们需要通过 `Utilities::MPI::sum`、`max`、`min` 或类似接口合并。于是你会看到许多变量成对出现：`local_*` 和 `global_*`。这不是啰嗦，而是在代码层面明确区分“我这个进程知道的”与“整个模拟知道的”。

## 逐块讲解

第一块通常是构造容器。构造时最关键的是大小从哪里来。如果大小来自 `n_q_points`，说明容器的每个元素对应一个积分点；如果来自 `n_compositional_fields()`，说明每个元素对应一个组分场；如果来自 `index_sets.*_partitioning`，说明容器对应一个并行自由度布局。不要把这些大小当成普通整数，它们其实是数据模型的一部分。

第二块是填充容器。填充可能来自有限元提取器，例如 `get_function_values()`；也可能来自几何模型、材料模型或用户参数。一个容器被填充之后，下一行代码往往立即进入循环，逐项读取并累计。初学者需要特别注意：有些容器会被函数覆盖，有些会累加，有些只在满足条件时更新。覆盖、累加、条件更新是三种完全不同的操作语义。

第三块是读取和计算。ASPECT 代码中常见 `for (unsigned int q = 0; q < n_q_points; ++q)`，这说明正在遍历积分点。遍历组分场时则常见 `for (unsigned int c = 0; c < this->n_compositional_fields(); ++c)`。当两层循环嵌套时，外层通常决定“哪个物理场”，内层决定“哪个空间位置”。理解这一点，你就能把很多看似复杂的公式还原成表格计算。

第四块是归约或输出。归约后的容器可能再被拆回 map、写入 `TableHandler`，或者拼成字符串返回。这里体现了 C++ 数据结构之间的转换：为了 MPI 通信，map 里的值可能被临时压成 vector；为了人类阅读，数字又被转成字符串；为了后续程序读取，统计量被加进表格。数据结构选择会随着阶段改变。

## 为什么这里选这个数据结构

选择容器不是背标准库清单，而是看数据的形状。如果数据是连续编号的一串数，顺序访问多，大小在运行时才知道，通常选 vector。如果数据数量固定且由维度决定，选 array 更清楚。如果数据天然按名字或 id 查询，map/set 让意图更强。如果对象生命周期复杂，智能指针比裸指针安全。如果数据按物理场分块，BlockVector 比单个大向量更符合有限元系统。

ASPECT 的代码风格还体现了一条经验：让数据结构暴露程序的不变量。例如 set 暗示没有重复边界；map 暗示每个 key 对应一个统计量；IndexSet 暗示只关心某个自由度子集；ComponentMask 暗示只选择某些分量；FullMatrix 暗示这是局部小矩阵而不是全局稀疏系统。读懂这些暗示，比死记函数名更重要。

## 初学者常见误区

第一个误区是把容器看成“数组”。数组只是底层形态，容器在源码中还表达了所有权、顺序、唯一性、映射关系和并行布局。第二个误区是忽略初始化值。`0.0`、`NaN`、`max()`、`lowest()` 各自有意义：有的表示可累加的零，有的表示尚未填充，有的用于求最小或最大。第三个误区是混淆局部与全局。在并行程序中，局部正确不等于全局正确，必须检查 MPI 汇总是否匹配操作语义。

第四个误区是用“能编译”代替“数据对应关系正确”。例如两个 vector 大小相同才能按同一 index 同步遍历；map 拆成 vector 后必须按同一个 set 顺序压入和取出；BlockVector 的 block index 必须和 `introspection` 一致。这些错误通常不会表现为语法错误，而会表现为物理结果奇怪。


## 常用操作/方法

- 构造：根据已知大小一次性创建容器，优先让初始值有明确含义。
- 访问：用 `[]` 访问已经存在的位置；需要检查存在性时使用 `find()`、`count()` 或显式边界判断。
- 填充：用 `push_back()`、`insert()`、赋值、`assign()` 或 block 赋值表达数据来源。
- 遍历：ASPECT 现代代码常用 range-for；当需要同步多个容器时，会使用显式 iterator 或 index。
- 汇总：局部容器先在本 MPI rank 上累积，再通过 `Utilities::MPI::*` 合并为全局结果。
- 命名：容器名通常包含物理意义，例如 `local_area_integral`，这比只叫 `values` 更适合大型科学代码。

## 可替代设计

在小程序里，你可能会用普通数组、多个独立变量或手写结构体完成同样任务。但 ASPECT 的规模决定了它更偏好通用容器。普通数组无法表达运行时数量，多个独立变量难以扩展到任意组分场，裸指针难以表达所有权，单个扁平向量难以让 Stokes、温度和组分字段保持清楚边界。替代设计不是不能用，而是要问：当模型从二维变三维、从一个组分变十个组分、从单进程变多进程时，它还能不能稳住。

一个实用判断是：如果容器里的元素有自然编号，使用顺序容器；如果元素需要按名字或 id 找，使用关联容器；如果对象不能复制且生命周期跨越多个函数，使用智能指针；如果数据来自有限元自由度，优先看 deal.II/ASPECT 已经提供的专用类型。这样做可以让代码更贴近领域语言。

## 阅读源码的方法

阅读本章对应源码时，可以按五步做笔记。第一步，圈出所有容器声明。第二步，给每个容器写一句话：它的每个元素代表什么。第三步，标出所有修改容器的语句。第四步，找出容器是否跨 MPI、跨函数或跨对象边界。第五步，写出如果容器为空、大小不匹配或没有某个 key 时会发生什么。这个方法慢一点，但非常适合入门大型 C++ 项目。

## 小结

本章的重点不是背下某一个函数，而是形成读代码的肌肉记忆：容器声明告诉你数据形状，填充语句告诉你数据来源，循环告诉你数据如何被消费，归约和返回语句告诉你数据最终服务于谁。只要沿着这条线读，ASPECT 里很多复杂 `.cc` 文件都会变得可拆解。

## 延伸讲解：把案例改写成伪代码

可以把本章案例抽象成四句话：准备容器，遍历 ASPECT 给出的对象，把物理量写进容器或从容器读出，最后把结果交还给框架。这个抽象适用于后处理器、材料模型、求解器和测试插件。真正困难的部分通常不是 C++ 语法，而是判断“对象”的粒度：有时对象是积分点，有时是单元，有时是边界，有时是自由度 block，有时是附加输出通道。

如果你正在学习 C++，建议先不要急着写模板代码。先用普通 `int`、`double` 和小 vector 模拟同样的数据流。例如把三个组分场看成三个篮子，把每个积分点的速度平方加到对应篮子里。等你能解释这个简化模型，再回到 ASPECT 源码看 `dim`、`FEValues`、`Tensor` 和 MPI。这样学习曲线会平滑很多。

最后要记住，ASPECT 的容器选择通常非常务实。它不会为了展示新语法而使用复杂类型；多数类型都在解决具体问题：谁拥有数据，数据是否重复，查询按编号还是按名字，是否需要并行通信，是否能高效传给 deal.II 求解器。把这些问题问清楚，你就已经掌握了 C++ 工程阅读的一大半。

## 课堂讲义扩展

shared_ptr 不是“更高级的指针”，而是共享生命周期的协议。AdditionalOutputs 的读取逻辑需要表达：如果这个扩展输出存在，就拿到一个共享引用并填充；如果不存在，逻辑块跳过。这里的 if 初始化语句同时完成查询和存在性判断。

把这一段落实到阅读动作上，可以做三件事。第一，回到源码中把本章容器的类型、变量名和初始化值抄成一张小表。第二，沿着函数执行顺序给每次修改编号，例如“第一次写入来自 FEValues，第二次写入来自局部积分，第三次写入来自 MPI 汇总”。第三，用一句中文说明这个容器不能被哪种更简单的变量替代。只要这三件事能说清楚，本章的 C++ 语法就不再是孤立知识，而是能服务大型科学代码阅读的工具。

进一步练习时，建议把案例缩小成不依赖 ASPECT 的玩具程序：用三到五个元素模拟积分点，用两个字段模拟温度和组分，用一两个 key 模拟边界 id。先在玩具程序中打印每一步容器内容，再回到真实源码看相同操作如何和网格、MPI、插件接口结合。这个来回切换的训练，比单纯背 STL 方法更有效。


# 详细版十页扩展：std::shared_ptr 在 ASPECT 中的完整教学案例

## 第 1 页：问题场景与学习入口

本章重新从问题出发，而不是从语法出发。源码锚点是 `source/material_model/melt_boukare.cc; cookbooks/phase_transition_kinetics/phase-transition-kinetics.cc`，核心函数或逻辑块是 `MaterialModel::evaluate 中的 AdditionalOutputs 查询`。这个案例之所以适合初学者，是因为它把 C++ 数据结构和 ASPECT 的科学计算任务绑在一起：代码不是为了展示容器而写容器，而是因为模型中确实有一组数据需要被组织、传递、检查和输出。

本章关注的数据形状是：共享所有权指针：多个逻辑块可以观察或填充同一个扩展输出对象。 这句话应该写在笔记第一页。只要你能稳定说出每个元素代表什么，就不会被模板、命名空间和物理术语吓住。ASPECT 的函数名很长，类型也很长，但大多数逻辑都可以还原成几件朴素的事：准备容器，从框架读取数据，在循环中修改容器，把容器交给下游。

读本章时建议同时打开源码。不要急着理解所有物理公式，先沿着容器移动：声明在哪里，第一次赋值在哪里，循环上界来自哪里，是否跨 MPI，返回或输出在哪里。大型 C++ 项目最怕“看了很多行但没有抓住数据线”。本章训练的就是抓数据线的能力。

## 第 2 页：这个数据结构在函数中的职责

在 `MaterialModel::evaluate 中的 AdditionalOutputs 查询` 中，`std::shared_ptr` 的职责可以概括为：模板查询、if 检查非空、operator-> 填充、框架管理生命周期。 这个职责决定了它的大小、初始化值、访问方式和错误边界。很多初学者会把容器看成“能装东西的盒子”，但在 ASPECT 里，容器更像一份合同。合同规定了每个位置的含义、谁能写、谁能读、什么时候可以认为数据完整。

判断职责时有三个问题特别关键。第一，容器是否只是临时缓冲？如果是，它应该在函数内部创建，循环中重复使用，避免外部状态污染。第二，容器是否表达接口？如果是，它的布局就不能随意改变，因为调用者和被调用者都依赖同一套解释。第三，容器是否参与并行通信？如果是，所有 rank 必须用相同顺序、相同大小和相同归约语义，否则结果可能看似合理却数值错误。

本章案例就是沿着这三个问题展开。你会看到 ASPECT 代码很少随手创建“匿名”的数据结构；即使是普通 `double` 列表，也会在变量名中写出 local/global、field/point、velocity/pressure 等语义。学会读变量名，是学会读 ASPECT 的第一步。

## 第 3 页：构造语句其实在写不变量

容器构造不是简单的内存申请。构造时的大小和默认值通常已经写下了程序不变量。大小来自积分点数量，说明每个元素对应一个 quadrature point；大小来自组分场数量，说明每个元素对应一个 compositional field；大小来自 `IndexSet` 或 block partitioning，说明容器必须服从并行自由度分布。

默认值同样重要。初始化为 `0.0` 通常表示后面要累加；初始化为 `numbers::signaling_nan<double>()` 表示这个值必须被后续代码覆盖，没覆盖就是错误；初始化为 `std::numeric_limits<double>::max()` 或 `lowest()` 表示后面要做最小/最大比较；空智能指针表示稍后根据参数选择具体对象；空 set/map/list 表示先建立集合或映射，再逐项填充。

因此，读构造语句时要把它翻译成中文。例如“创建一个大小等于组分场数量的局部积分数组，每项从 0 开始，后面会累加该组分区域内的贡献”。这种翻译比背 API 更有用。你翻译得越具体，越容易发现后面的循环有没有错。

## 第 4 页：填充阶段的来源检查

填充阶段回答“数据从哪里来”。在 ASPECT 中，来源可能是 `FEValues`、`FEFaceValues`、`MaterialModelInputs`、`MaterialModelOutputs`、`ParameterHandler`、几何模型、插件注册表或另一个向量 block。每个来源都有自己的前提：`FEValues` 必须先 `reinit(cell)`，面上的 `FEFaceValues` 必须知道 cell 和 face，材料模型输入必须和 evaluation point 数量一致，BlockVector 必须有兼容的 partitioning。

对 `std::shared_ptr` 来说，填充阶段尤其要区分“覆盖”和“累加”。覆盖表示旧值不再有意义，例如把当前单元的有限元值写入积分点缓冲；累加表示旧值代表已经处理过的部分，例如积分和统计量；追加表示顺序增长，例如插件依赖和输出列表；插入表示集合或映射关系发生变化，例如 boundary id 或 name-id 映射。

调试时可以在填充前后打印大小和少量元素。不要打印整个大向量，科学计算里数据可能非常多。更好的方法是打印第一个、最后一个、最小值、最大值、是否包含 NaN、是否为空。对于并行代码，还要只在一个 rank 上打印，或者把每个 rank 的局部信息写清楚。

## 第 5 页：遍历阶段的下标语义

遍历是 ASPECT 容器错误最容易发生的地方。一个 `for` 循环的上界不是普通整数，它通常携带领域含义。`q` 多半表示积分点，`c` 多半表示组分场，`d` 多半表示空间维度，`i` 可能是插件、相、自由度或普通计数。读代码时要给每个循环变量命名：不要只说“外层循环”和“内层循环”，要说“外层遍历组分场，内层遍历积分点”。

如果两个容器在同一个循环里使用同一个下标，它们必须共享同一个坐标系。例如 `values[q]` 和 `weights[q]` 都要对应第 q 个积分点；`composition[q][c]` 和 `temperature[q]` 都要对应第 q 个 evaluation point；`global_values[index]` 和 `boundary_id` 的关系必须来自前面同一套遍历顺序。这里没有复杂语法，只有非常朴素但非常要命的对应关系。

建议你在教材旁边画一张小表。表头写 q=0,1,2 或 c=0,1,2，单元格里写对应物理量。把代码中的 `[]` 下标都标到表格里。这个办法看起来慢，但对大型模板代码尤其有效，因为它把抽象类型还原成了可检查的数据布局。

## 第 6 页：修改阶段与状态变化

修改容器时要问“旧状态是否还需要”。`+=` 保留旧状态并累加；`=` 覆盖旧状态；`push_back` 在末尾添加新状态；`insert` 尝试加入一个 key；`reset` 可能销毁旧对象；`block(i) = ...` 可能复制一个物理子向量。相同的符号在不同容器里语义也不完全相同，比如 `operator[]` 对 vector 是按位置访问，对 map 则可能默认创建 key。

在 ASPECT 中，状态变化还经常与数学步骤对应。积分循环中的 `+=` 表示把一个积分点贡献加入总量；求解器中的 block 赋值表示把当前线性化点拷贝成初始猜测；材料模型中的二维数组转置表示从有限元输出布局转换成材料模型输入布局；插件管理中的智能指针移动表示对象所有权从未排序列表进入排序列表。

初学者要学会把状态变化写成一句话，而不是只看符号。比如“把第 c 个组分场在第 q 个积分点的速度平方乘以积分权重后累加到第 c 个局部积分缓存”。这一句话虽然长，却能准确防止你把 q 和 c 写反。

## 第 7 页：常用操作/方法

本章相关操作可以整理成一张方法清单。构造类操作负责确定大小和初始值；访问类操作负责读取已有元素；修改类操作负责改变内容；遍历类操作负责维持顺序；接口类操作负责把容器交给 ASPECT 或 deal.II。

- 构造：根据 `n_q_points`、`n_compositional_fields`、`dim`、`IndexSet` 或参数选择容器大小。
- 访问：用 `[]`、`block(i)`、`first/second`、`operator->` 或迭代器读取元素。
- 修改：用赋值、`+=`、`insert`、`push_back`、`reset`、`std::move` 或矩阵操作改变状态。
- 遍历：用 range-for 表达“遍历所有已选对象”，用 index loop 表达“下标具有物理意义”。
- 检查：用 `size()`、`empty()`、断言、空指针判断、NaN 哨兵或 MPI 后的全局值检查不变量。

记 API 时不要孤立记。比如 `size()` 的问题不是“怎么调用”，而是“这个 size 代表什么物理数量”；`insert()` 的问题不是“怎么插入”，而是“重复元素是否应被忽略”；`std::move` 的问题不是“怎么写”，而是“移动后原对象还能不能用”。

## 第 8 页：为什么这里不用更简单的写法

很多学习者会问：为什么不用普通数组，为什么不用几个变量，为什么不用裸指针，为什么不全部用 vector？答案是：ASPECT 的数据规模和接口边界太复杂，简单写法很快会失去语义。普通数组不表达运行时大小；几个变量无法扩展到任意字段；裸指针不表达所有权；统一用 vector 会丢掉集合唯一性、key-value 映射、分块物理变量和有限元组件选择。

`std::shared_ptr` 在本章中并不是“炫技”，而是在表达约束。它告诉读者数据是否有顺序、是否唯一、是否按 key 查询、是否共享生命周期、是否分块、是否固定长度、是否只选择一部分自由度。好的数据结构让错误更难写出来，也让代码审查者更容易看出意图。

当然，替代方案有时是合理的。小型教学程序可以用更简单的类型模拟；性能瓶颈处可能会选更低层的数据布局；接口稳定后也可能引入具名 struct 替代 pair。关键不是迷信某个容器，而是能说出选择和代价。

## 第 9 页：常见错误和调试路线

本章最常见的错误有五类。第一，大小错：容器大小和循环上界不是同一个概念。第二，方向错：二维数据把 `[q][c]` 和 `[c][q]` 写反。第三，状态错：本该累加却覆盖，本该覆盖却累加。第四，接口错：返回值、智能指针或 block 布局的含义没有和调用者对齐。第五，并行错：局部值直接当全局值使用。

调试路线建议固定下来。先检查容器大小，再检查第一项和最后一项，再检查是否有 NaN 或空指针，再检查循环边界，最后检查 MPI 归约或对象生命周期。不要一上来就改公式。很多“物理结果不对”的问题，本质只是容器写错位置。

ASPECT 源码里的断言值得模仿。只要你知道一个假设必须成立，就应该让代码说出来：block 数必须为 2，边界集合必须只有一个元素，压力 block 必须在预期位置，字段名必须存在，矩阵维度必须匹配。断言是大型 C++ 代码给未来读者留下的护栏。

## 第 10 页：课后练习与源码复读

课后练习分三层。第一层，脱离 ASPECT 写一个 20 行小程序，只模拟 `std::shared_ptr` 的核心操作。第二层，回到 `source/material_model/melt_boukare.cc; cookbooks/phase_transition_kinetics/phase-transition-kinetics.cc`，把本章提到的每个容器声明用注释标出“元素含义”。第三层，用 `rg` 搜同一数据结构在其他 `.cc` 文件中的使用，比较场景是否相同。

建议练习题：

1. 写出本章案例的数据流：输入是什么，临时容器是什么，输出是什么。
2. 找出所有修改容器的语句，把它们分成覆盖、累加、追加、插入、移动五类。
3. 给每个循环变量写出物理含义，说明为什么上界是这个数量。
4. 假设容器为空、字段数为零或指针为空，说明函数会怎样表现。
5. 设计一个断言，能提前发现本章最可能发生的一类错误。
6. 写一个小型 C++ 例子，不使用 ASPECT 类型，但保留同样的数据结构操作。

读完这一页，再回到本章开头。你会发现同一个源码片段不再只是模板和长类型名，而是一条清楚的数据路线：ASPECT 框架给出对象，容器承接对象，循环改写对象，接口交还对象。能看见这条路线，就是真正进入大型 C++ 科学代码的开始。
